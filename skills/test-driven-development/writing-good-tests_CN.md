# 编写优秀的测试

**在以下情况下加载本参考：**编写或修改测试、添加 mock，或为测试添加清理/辅助方法。

## 概述

测试的存在是为了捕获一个具体的破坏。这里的一切都由两个原则支配：

```
1. 每个测试都要说明它捕获的破坏
2. 每个测试都要测试真实对象
```

严格的 TDD 自然会同时做到这两点：一个先编写、并针对真实代码观察到失败的测试，已经证明它能够失败；只有当真实依赖证明过慢或属于外部依赖时，测试才有理由使用 mock。

## 原则 1：明确测试要捕获的破坏

在编写测试主体之前，回答：**什么生产代码变更会让这个测试失败——而这个变更是错误还是决策？**测试之所以值得存在，是因为它能捕获错误分支、缺少的副作用、错误参数、边界情况或被破坏的契约。

**独立推导期望值。**使用字面量和手工检查过的 fixture；带有字面量 `want` 值的表驱动测试是首选形式。由被测代码或其辅助函数计算出的期望值，无论代码做什么都会通过：

```typescript
// ❌ Mirror assertion: the same builder computes both sides — always true
const expected = buildSearchQuery({ tag: 'urgent' });
expect(buildSearchQuery({ tag: 'urgent' })).toBe(expected);

// ✅ Hand-derived literal
expect(buildSearchQuery({ tag: 'urgent' })).toBe('tag:"urgent"');
```

**不要写变更检测器。**如果测试只会因有意的决策而失败——常量的值、确切的消息措辞、私有结构——那么它会在重新设计时触发，却会对错误视而不见。测试依赖该决策的行为：不要测试 `expect(MAX_RETRIES).toBe(5)`，而要测试“失败调用会重试 5 次，第 6 次尝试永远不会发生”。

**测试行为，而不是文本。**断言脚本、技能或配置包含某一行确切文本，只能证明源文件就是这个源文件。针对受控输入运行脚本，并断言输出、副作用或退出码。指导 agent 的文档，应通过消费它的 agent 的行为来测试（`superpowers:writing-skills`）；面向人的 prose 根本不需要测试。

**测试你的代码，而不是框架。**在边界处测试你的代码所作出的契约——你注册的路由、你发出的查询、你生成的 payload。上游机制由它们的维护者负责测试（经典例子：断言你的路由器调用了已注册的处理器——那是框架的测试，不是你的测试）。当上游行为确实让你感到意外时，编写一个狭窄的特征描述测试，明确写出这个假设。同样的边界也适用于你的代码内部：只有在构造函数、getter、常量和简单转发会进行校验、规范化、提供默认值、推导、强制执行或产生副作用时，才值得测试它们；否则，应断言依赖它们的第一个用户可见结果。

### 闸门函数

```
在编写测试主体之前：
  明确会让这个测试失败的生产代码变更。

  无法明确                → 围绕可观察行为重新设计
  “源文本发生了变化”      → 运行产物并断言其效果
  只有有意的决策          → 这是变更检测器；测试依赖该决策的行为

  确认期望值不是使用被测代码推导出来的。
  如果它复用了代码的逻辑或辅助函数：
    用字面量或手工检查过的 fixture 替换它
```

## 原则 2：测试真实对象

**mock 不值得获得任何断言。**当 mock 存在时 mock 断言通过、当 mock 不存在时失败——它无法说明组件的任何事情。断言真实组件的行为；如果你检查的就是 mock，那么取消 mock 或删除断言。

```typescript
// ✅ Real behavior
expect(screen.getByRole('navigation')).toBeInTheDocument();

// ❌ Mock existence
expect(screen.getByTestId('sidebar-mock')).toBeInTheDocument();
```

**你的伙伴的纠正：**“我们是在测试 mock 的行为吗？”

**在正确的层级使用 mock。**在替换真实方法之前，了解它的每一个副作用；mock 缓慢或外部的操作，同时保留测试所依赖的真实行为。不确定时，先针对真实实现运行测试，观察实际需要发生什么。

```typescript
// ❌ The mock swallows the config write that duplicate detection reads
vi.mock('ToolCatalog', () => ({
  discoverAndCacheTools: vi.fn().mockResolvedValue(undefined)
}));

// ✅ Mock only the slow server startup; the config write stays real
vi.mock('MCPServerManager');
```

**让测试替身具体化。**当参数、调用次数或顺序属于契约的一部分时，要对它们进行断言；一个接受任何内容的 fake 什么也验证不了。为每个分支（成功、错误、格式错误）提供自己的 fixture 或 spy，这样错误分支就无法满足期望。

**完整复刻真实数据。**让 mock 的完整结构与现实中的结构一致——包括所有文档化字段，而不只是测试读取的字段。如果下游代码读取了被省略的字段，不完整的 mock 会静默失败：测试通过了，但集成却会中断。

**生产类只携带生产方法。**只有测试需要的清理逻辑应放在测试工具中，绝不要在生产类上增加 `destroy()`。问自己：这个方法是否只从测试中调用？这个类是否拥有该资源的生命周期？如果答案不对，就应该放进测试工具。

**优先使用真实组件，而不是复杂 mock。**当 mock 的设置已经超过测试逻辑、mock 缺少真实组件拥有的方法，或测试会因 mock 改变而中断时，切换到使用真实组件的集成测试。**你的伙伴会问：**“这里真的需要使用 mock 吗？”

### 闸门函数

```
在添加 mock 或测试辅助函数之前：
  列出真实方法的副作用；保留测试所依赖的真实副作用——在更低层级
  mock 缓慢/外部的操作。

  mock 响应要完整复刻真实结构。

  只被测试调用的方法应放在测试工具中，而不是生产代码中。

  准备断言 mock 本身？
    取消 mock 或删除断言。
```

## 测试应与实现一起交付

TDD 循环——失败测试、最小实现、重构——才是“完成”的含义。交付行为需要的测试，而且只交付这些测试：简单代码和面向人的 prose 不需要测试，而为了满足流程编写的测试会永久增加维护成本。

## 变异检查

完成之前，在脑中对生产代码进行变异；每一种现实的变异都应该至少让一个测试失败：

- 错误的常量或参数
- 错误的分支处理器
- 缺少状态变更或副作用
- 空的或默认的返回值
- 缺少对零值、空值、nil、未授权或格式错误输入的校验

没有测试捕获的变异，说明该行为没有受到保护——或者测试是同义反复。

## 快速参考

| 当你…… | 应该…… |
|-------------|-----|
| 编写任意测试 | 明确它捕获的破坏——是错误，而不是决策 |
| 构建期望值 | 手工推导；绝不要使用被测代码 |
| 测试脚本或文档 | 运行它/对它的消费者做压力测试；绝不要 grep 它的文本 |
| 想测试依赖项 | 测试你的边界契约，而不是对方文档化的机制 |
| 想断言一个 mock 元素 | 测试真实组件，或取消 mock |
| 准备 mock 一个方法 | 了解它的副作用；在缓慢/外部的层级进行 mock |
| 构建 mock 响应 | 完整复刻真实结构 |
| 需要只有测试使用的清理逻辑 | 放进测试工具 |
| 发现 mock 设置不断膨胀 | 切换到使用真实组件的集成测试 |
| 完成一个测试文件 | 运行变异检查 |

## 警告信号

- 设置与断言共享同一个对象，保证了相等
- 测试只能通过 panic、崩溃或缺少选择器来失败
- 测试会因每一个有意的变更而失败，却从不因意外破坏而失败
- 期望值隐藏在循环、构建器或辅助函数之后
- 测试 grep 源文本，或断言某个已删除的符号仍保持删除状态
- 即使只剩下框架，测试仍然会有意义
- 测试只是为了覆盖率而存在，没有检查副作用或结果
- 断言检查 `*-mock` 测试 ID，或者移除 mock 后就会失败
- 某个方法只从测试文件中调用
- mock 设置占了测试一半以上，或者你无法解释为什么需要这个 mock
- “以防万一”而进行 mock
