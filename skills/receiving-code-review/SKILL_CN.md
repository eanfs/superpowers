# 接收代码审阅

## 概述

代码审阅需要技术评估，而不是情绪表演。

**核心原则：**先验证再实现。先询问再假设。技术正确性高于社交舒适。

## 响应模式

```
收到代码审阅反馈时：

1. 阅读：完整阅读反馈，不作反应
2. 理解：用自己的话重述需求（或提出问题）
3. 验证：对照代码库实际情况检查
4. 评估：对这个代码库来说技术上正确吗？
5. 响应：技术性确认或有理有据地提出异议
6. 实现：一次处理一项，每项都进行测试
```

## 禁止的响应

**绝不要：**
- “你完全正确！”（明确违反指令文件）
- “好观点！”/“出色的反馈！”（表演式回应）
- “我现在就来实现”（尚未验证之前）

**改为：**
- 重述技术需求
- 提出澄清问题
- 如果不对，基于技术理由提出异议
- 直接开始工作（行动胜于言辞）

## 处理不清楚的反馈

```
如果任何一项不清楚：
  停止——暂时不要实现任何内容
  针对不清楚的项目请求澄清

原因：项目之间可能有关联。理解不完整 = 实现错误。
```

**示例：**
```
你的人工协作者：“修复 1-6”
你理解 1、2、3、6，对 4、5 不清楚。

❌ 错误：现在先实现 1、2、3、6，之后再询问 4、5
✅ 正确：“我理解 1、2、3、6。在继续之前，需要澄清 4 和 5。”
```

## 针对来源的处理

### 来自你的人工协作者
- **可信**——理解后实现
- **范围不清时仍然要询问**
- **不要表演式赞同**
- **直接行动**或给出技术性确认

### 来自外部审阅者
```
实现之前：
  1. 检查：对这个代码库来说技术上正确吗？
  2. 检查：会破坏现有功能吗？
  3. 检查：当前实现的原因是什么？
  4. 检查：在所有平台/版本上都能工作吗？
  5. 检查：审阅者是否理解完整上下文？

如果建议似乎不对：
  基于技术理由提出异议

如果无法轻易验证：
  明确说明：“没有 [X]，我无法验证这一点。应该[调查/询问/继续]吗？”

如果与人工协作者先前的决定冲突：
  先停下，与人工协作者讨论
```

**你的人工协作者的规则：**“外部反馈——保持怀疑，但认真检查。”

## “专业”功能的 YAGNI 检查

```
如果审阅者建议“正确地实现”：
  在代码库中搜索实际使用情况

  如果未使用：“这个端点没有被调用。删除它（YAGNI）？”
  如果已使用：那么正确实现它
```

**你的人工协作者的规则：**“你和审阅者都向我汇报。如果我们不需要这个功能，就不要添加它。”

## 实现顺序

```
对于多项反馈：
  1. 先澄清所有不清楚的内容
  2. 然后按以下顺序实现：
     - 阻塞问题（破坏功能、安全问题）
     - 简单修复（拼写错误、导入）
     - 复杂修复（重构、逻辑）
  3. 单独测试每项修复
  4. 验证没有回归
```

## 何时提出异议

在以下情况提出异议：
- 建议会破坏现有功能
- 审阅者缺少完整上下文
- 违反 YAGNI（未使用的功能）
- 对于当前技术栈来说技术上不正确
- 存在遗留/兼容性原因
- 与你的人工协作者的架构决定冲突

**如何提出异议：**
- 使用技术理由，而不是防御性表态
- 提出具体问题
- 引用正常工作的测试/代码
- 如果涉及架构问题，让你的人工协作者参与

**如果你不自在于当面提出异议：**说出这种紧张感，然后把你发现的问题告诉你的协作者。他们会欣赏你的诚实。

## 确认正确的反馈

当反馈**确实正确**时：
```
✅ “已修复。[改动内容的简短说明]”
✅ “发现得好——[具体问题]。已在[位置]修复。”
✅ [直接修复，并在代码中展示]

❌ “你完全正确！”
❌ “好观点！”
❌ “谢谢你发现这个问题！”
❌ “感谢[任何内容]！”
❌ 任何表达感谢的说法
```

**为什么不说感谢：**行动会说明一切。代码本身就表明你听到了反馈。

**如果你发现自己正要写“谢谢”：**删除它。直接陈述修复内容。

## 优雅地纠正你的异议

如果你提出异议后发现自己错了：
```
✅ “你说得对——我检查了 [X]，它确实是 [Y]。现在实现。”
✅ “已经验证，你是对的。我最初的理解因为[原因]而错误。正在修复。”

❌ 长篇道歉
❌ 为自己提出异议辩解
❌ 过度解释
```

客观地说明更正，然后继续。

## 常见错误

| 错误 | 修复 |
|---------|---------|
| 表演式赞同 | 陈述需求或直接行动 |
| 盲目实现 | 先对照代码库验证 |
| 批量实现后再测试 | 一次修复一项，每项测试 |
| 假设审阅者是对的 | 检查是否会造成破坏 |
| 避免提出异议 | 技术正确性高于舒适感 |
| 部分实现 | 先澄清所有项目 |
| 无法验证却继续 | 说明限制并请求指示 |

## 真实示例

**表演式赞同（坏）：**
```
审阅者：“删除遗留代码。”
❌ “你完全正确！我来删除……”
```

**技术验证（好）：**
```
审阅者：“删除遗留代码。”
✅ “正在检查……构建目标是 10.15+，这个 API 需要 13+。为了向后兼容必须保留遗留代码。当前实现的 bundle ID 有误——是修复它，还是放弃对 13 之前版本的支持？”
```

**YAGNI（好）：**
```
审阅者：“实现正确的指标跟踪，包括数据库、日期筛选和 CSV 导出。”
✅ “搜索了代码库——没有任何内容调用这个端点。删除它（YAGNI）？还是有我遗漏的使用方？”
```

**不清楚的项目（好）：**
```
你的人工协作者：“修复项目 1-6。”
你理解 1、2、3、6，对 4、5 不清楚。
✅ “理解 1、2、3、6。在实现之前需要澄清 4 和 5。”
```

## GitHub 线程回复

在 GitHub 上回复行内审阅评论时，应回复评论线程（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），而不是发布顶层 PR 评论。
