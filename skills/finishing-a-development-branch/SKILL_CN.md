# 完成开发分支

## 概述

**核心原则：**验证测试 → 检测环境 → 展示选项 → 执行选择 → 清理。

**开始时宣布：**“我正在使用 finishing-a-development-branch 技能来完成这项工作。”

## 第 1 步：验证测试

运行项目的完整测试套件（`npm test` / `cargo test` / `pytest` / `go test ./...`）。

**如果测试失败，**报告失败并停止——菜单要等测试全绿后才出现：

```
测试失败（<N> 个失败）。完成前必须修复：

[展示失败]
```

**如果测试通过：**继续第 2 步。

## 第 2 步：检测环境

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
# 现在捕获，因为第 5 步会改变目录
# 第 6 步清理时需要这个值
WORKTREE_PATH=$(git rev-parse --show-toplevel)
```

这会决定展示哪个菜单以及如何清理：

| 状态 | 菜单 | 清理 |
|---------|---------|---------|
| `GIT_DIR == GIT_COMMON`（普通仓库） | 标准 3 个选项 | 无需清理工作区 |
| `GIT_DIR != GIT_COMMON`，命名分支 | 标准 3 个选项 | 基于来源（见第 6 步） |
| `GIT_DIR != GIT_COMMON`，分离 HEAD | 精简 2 个选项（无合并） | 外部管理——保留原处 |

## 第 3 步：确定基分支

基分支就是这项工作从哪里分叉出来的——通常会在计划、对话或分支的上游中注明。如果还不知道，就询问：“这个分支从 <你最好的猜测> 分出来——这样对吗？”在合并前确认，因为合并到错误的基分支很难撤销。

## 第 4 步：展示选项

**普通仓库和命名分支工作区——准确展示以下 3 个选项：**

```
实现完成。你想怎么处理？

1. 在本地合并回 <base-branch>
2. 推送并创建 Pull Request
3. 保持分支原样（我稍后处理）

选择哪个选项？
```

**分离 HEAD——准确展示以下 2 个选项：**

```
实现完成。你当前处于分离 HEAD（由外部管理的工作区）。

1. 作为新分支推送并创建 Pull Request
2. 保持原样（我稍后处理）

选择哪个选项？
```

严格按上面写出的内容展示菜单——保持简洁，所有选项都必须来自上面的列表。只有你的人工协作者明确要求时才会丢弃工作（见下方“如果你的人工协作者要求丢弃工作”）。等待他们的回答；集成决策由他们作出。

## 第 5 步：执行选择

### 选项 1：本地合并

```bash
# 获取主仓库根目录，确保 CWD 安全
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"

# 先合并——在删除任何内容前验证成功
git checkout <base-branch>
git pull
git merge <feature-branch>

# 在已合并结果上验证测试
<test command>
```

如果合并结果上的测试失败：停止，保留工作区和分支并进行调查——没有任何内容被推送，因此合并仍是本地的、可恢复的。

一旦合并结果通过：清理工作区（第 6 步），然后删除分支：

```bash
git branch -d <feature-branch>
```

### 选项 2：推送并创建 PR

```bash
git push -u origin <feature-branch>
# 从分离 HEAD 推送时，在远程命名新分支：
# git push origin HEAD:refs/heads/<new-branch>
```

然后使用代码托管平台的工具针对 <base-branch> 创建 pull/merge request——如果有 CLI 就使用 CLI，或者使用推送时大多数平台打印的创建 URL——并遵循仓库现有的 PR 模板和约定（如果有），然后向你的人工协作者报告 URL。

保留工作区——你的人工协作者会在其中迭代处理 PR 反馈。

### 选项 3：保持原样

报告：“保留分支 <name>。工作区保留在 <path>。”

### 如果你的人工协作者要求丢弃工作

只有在收到明确要求丢弃工作的请求时才走此路径。先确认：

```
这将永久删除：
- 分支 <name>
- 所有提交：<commit-list>
- 工作区 <path>

输入 'discard' 以确认。
```

等待完全匹配的确认。确认到达后：

```bash
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"
```

然后清理工作区（第 6 步）并强制删除分支：

```bash
git branch -D <feature-branch>
```

## 第 6 步：清理工作区

**选项 1 和已确认的丢弃操作会执行此步骤。**选项 2 和选项 3 始终保留工作区。两者的调用方都已切换到主仓库根目录——必须在工作区外运行移除工作区的命令——并使用第 2 步捕获的 `GIT_DIR`/`GIT_COMMON`/`WORKTREE_PATH` 值，这些值是在改变目录之前捕获的。

**如果 `GIT_DIR == GIT_COMMON`：**普通仓库，无需清理工作区。完成。

**如果 `WORKTREE_PATH` 位于 `.worktrees/` 或 `worktrees/` 下：**Superpowers 创建了这个工作区——我们负责清理：

```bash
git worktree remove "$WORKTREE_PATH"
git worktree prune  # 自我修复：清理任何过期注册
```

**如果移除被拒绝**（“contains modified or untracked files”）：工作区中有其他地方不存在的文件——未提交的计划、笔记或临时工作。绝不要自行使用 `--force`。向你的人工协作者展示风险所在，并询问：

```bash
git -C "$WORKTREE_PATH" status --porcelain -uall
```

```
工作区移除被拒绝——以下文件从未提交：

<文件列表>

1. 在清理前将它们提交到 <branch>
2. 将它们移动到 <main repo root>
3. 删除它们（无法恢复）

选择哪个？
```

执行所选操作，然后移除工作区。

**其他情况：**宿主环境负责管理此工作区——将其保留原处。如果你的平台提供工作区退出工具，就使用它。

## 快速参考

| 选项 | 合并 | 推送 | 保留工作区 | 清理分支 |
|---------|---------|---------|---------|---------|
| 1. 本地合并 | 是 | - | - | 是 |
| 2. 创建 PR | - | 是 | 是 | - |
| 3. 保持原样 | - | - | 是 | - |
| 丢弃（仅限明确请求） | - | - | - | 是（强制） |

## 常见合理化借口

| 借口 | 现实 |
|---------|---------|
| “本会话早些时候测试通过了” | 在你即将集成的树上运行测试套件。绿色运行只能证明它运行时对应的那棵树。 |
| “他们显然想让我合并” | 集成是你的人工协作者的决定。展示菜单并等待。 |
| “他们似乎已经完成这个功能了——我就提供丢弃选项” | 菜单必须完整按上面的内容展示。只有你的人工协作者明确说出要丢弃时，才会发生丢弃。 |
| “‘好，删掉它’算确认” | 只有输入 `discard` 才授权删除。 |
| “PR 已经创建，工作区现在只是杂物” | PR 反馈需要在该工作区中修复。工作落地之前都要保留它。 |
| “这个其他工作区看起来过时了——我也清理掉它” | 只清理位于 `.worktrees/` 或 `worktrees/` 下的工作区。其他一切都属于宿主环境。 |
| “移除被拒绝——`--force` 只是完成清理” | 拒绝意味着文件只存在于该工作区。`--force` 会永久销毁它们。展示给你的人工协作者并询问。 |
| “合并结果失败可能只是偶发问题” | 合并结果失败会停止一切。保留分支和工作区，继续调查。 |
| “基分支显然是 main” | 确认分叉点或进行询问。合并到错误基分支很难撤销。 |
| “推送被拒绝——强制推送可以解决” | 被拒绝的推送表示远程已发生变化。先调查；只有你的人工协作者明确要求时才强制推送。 |
