# 任务审阅者提示词模板

在派遣任务审阅子代理时使用此模板。审阅者只读取一次任务差异，并返回两个结论：规范符合性和代码质量。

**目的：**验证单个任务的实现符合其需求（不多不少），并且构建良好（清晰、经过测试、可维护）。

```
Subagent (general-purpose):
  description: "审阅任务 N（规范 + 质量）"
  model: [MODEL — REQUIRED: choose per SKILL.md Model Selection; an omitted
         model silently inherits the session's most expensive one]
  prompt: |
    你正在审阅一个任务的实现：先判断它是否符合需求，再判断它是否构建良好。这是任务范围内的质量门禁，不是合并审阅——所有任务完成后会单独进行广泛的整分支审阅。

    ## 请求内容

    阅读任务简报：[BRIEF_FILE]

    约束该任务的规范/设计中的全局约束：
    [GLOBAL_CONSTRAINTS]

    ## 实现者声称构建的内容

    阅读实现者的报告：[REPORT_FILE]

    ## 待审阅的差异

    **基准：**[BASE_SHA]
    **头部：**[HEAD_SHA]
    **差异文件：**[DIFF_FILE]

    仅读取一次差异文件——其中包含提交列表、统计摘要，以及带周围上下文的完整差异；它就是你查看变更的依据。差异中的上下文行就是变更文件的内容：除非必须判断的代码块在中间被截断，否则不要单独读取变更文件——如果确实被截断，请在报告中说明。不要重新运行 Git 命令。如果差异文件缺失，请自行获取：
    `git diff --stat [BASE_SHA]..[HEAD_SHA]` 和
    `git diff [BASE_SHA]..[HEAD_SHA]`。
    不要爬取更广泛的代码库。只有为了评估一个你能明确指出的具体风险时，才检查差异之外的代码——每个明确风险只进行一次聚焦检查，并在报告中说明风险和检查内容。如果差异涉及锁顺序、函数或 API 契约，或共享可变状态，检查调用点属于合理的跨领域风险检查。

    你在此检出目录中的审阅必须是只读的。不得以任何方式修改工作树、索引、HEAD 或分支状态。

    ## 不得派遣子代理

    独立完成全部审阅。绝不要派遣子代理审阅差异的一部分，也绝不要再派遣另一名审阅者征求第二意见。这个流程已经提供了该工作能获得的所有审阅席位；你派遣的审阅者会以完整成本重复其中一个席位，而且其结论在流程中不计入。如果差异太大，无法一遍完成，就自行分阶段审阅，并在报告中说明。

    ## 不要相信报告

    将实现者的报告视为未经验证的代码声明。报告可能不完整、不准确或过于乐观。报告中的设计理由同样是声明，例如“根据 YAGNI 将其保留如此”、“有意保持简单”或任何其他为自己评分的解释。根据代码本身的优点进行判断——陈述的理由绝不会降低发现的严重程度。

    ## 测试

    实现者已经运行了测试，并为恰好对应这段代码提供了带 TDD 证据的结果。不要为了确认报告而重新运行测试。只有在阅读代码时产生了具体疑问，且现有运行结果无法回答时，才运行测试——并且只能运行聚焦测试，绝不能运行整个包的测试套件、竞态检测器或高次数循环。如果看起来需要进行重量级验证，请在报告中建议，而不是自行运行。如果你无法在此环境中运行命令，请写明你会运行的测试。

    实现者报告的警告或其他噪声也是发现——测试输出应当是干净的。

    你看不到的证据不等于不存在证据。如果报告或测试证据看起来被截断，或者你找不到其中声称的结果，请重新读取报告指定路径的文件；如果文件确实缺失或损坏，请将其作为控制器的缺口报告。重新运行测试套件来生成你没能读到的内容，不是验证；证据不可读也不能使其失效。

    ## 第一部分：规范符合性

    将差异与“请求内容”进行比较：

    - **缺失：**跳过、遗漏或声称完成但没有实现的需求
    - **额外：**未请求的功能、过度工程化、不需要的“锦上添花”
    - **误解：**实现了正确的功能，但方式错误，或解决了错误的问题

    如果简报为每个文件分别列出了变更（一次批量派遣），请逐文件将差异与清单进行比较：每个列出的文件都必须有对应的差异块。差异完全没有触及的列出文件属于缺失发现，无论其余部分多么整洁。

    如果某项需求无法仅凭差异验证（它存在于未变更的代码中，或跨越多个任务），请将其作为 ⚠️ 项报告，而不要扩大搜索范围。

    ## 第二部分：代码质量

    **代码质量：**
    - 关注点是否清晰分离？
    - 错误处理是否恰当？
    - 是否在避免过早抽象的同时做到 DRY？
    - 是否处理了边界情况？

    **测试：**
    - 新增和变更的测试是否验证了真实行为，而不是 mock？
    - 是否覆盖了该任务的边界情况？

    **结构：**
    - 每个文件是否都承担一个清晰的职责，并有定义明确的接口？
    - 单元是否被拆分到可以独立理解和测试的程度？
    - 实现是否遵循计划中的文件结构？
    - 此变更是否创建了已经过大的新文件，或显著增大了现有文件？（不要标记之前就存在的文件大小——只关注此变更造成的影响。）

    报告应当指向证据：每个发现以及任何你本来会只回答“是”的检查，都提供文件:行号引用。紧凑且带行号的报告能为控制器提供全部所需信息。

    你的最终消息就是报告本身：直接从规范符合性结论开始。每一行都必须是结论、带文件:行号的发现，或你运行的检查——不要写前言、过程叙述或结束总结。

    ## 校准标准

    按实际严重程度对问题分类。并非所有问题都是 Critical。Important 意味着该任务在修复前不可信：不正确或脆弱的行为、遗漏的需求，或你会因此阻止合并的可维护性损害——逻辑块的逐字重复、被吞掉的错误、没有断言任何内容的测试。“覆盖面可以更广”和润色建议属于 Minor。在列出问题前，先肯定做得好的地方——准确的正面反馈有助于实现者信任其余意见。

    如果计划或简报明确要求某项内容，而本评估标准将其视为缺陷（例如没有断言任何内容的测试、逐字重复的逻辑块），那就是发现——将其报告为 Important，并标记为 plan-mandated。计划的作者身份不会替实现打分；由人来决定。

    ## 输出格式

    ### 规范符合性

    - ✅ 规范符合 | ❌ 发现问题：[缺失/额外/误解的内容，并提供文件:行号引用]
    - ⚠️ 无法从差异验证：[无法仅凭差异验证的需求，以及控制器应检查的内容——与 ✅/❌ 结论一并报告所有可验证内容]

    ### 优点
    [具体说明哪些地方做得好。]

    ### 问题

    #### Critical（必须修复）
    #### Important（应当修复）
    #### Minor（锦上添花）

    对于每个问题：文件:行号、问题是什么、为什么重要、如何修复（如果不明显）。

    ### 评估

    **任务质量：**[Approved | Needs fixes]

    **理由：**[1–2 句技术评估]
```

**占位符：**
- `[MODEL]`——必需：根据 SKILL.md Model Selection 选择审阅者模型
- `[BRIEF_FILE]`——必需：任务简报文件（`scripts/task-brief PLAN N` 会打印路径；就是实现者使用的同一个文件）
- `[GLOBAL_CONSTRAINTS]`——约束该任务的计划“全局约束”章节或规范中的约束，原样复制：确切值、格式，以及组件之间声明的关系（不是流程规则——本模板已经包含流程规则）
- `[REPORT_FILE]`——必需：实现者写入详细报告的文件
- `[BASE_SHA]`——此任务之前的提交
- `[HEAD_SHA]`——当前提交
- `[DIFF_FILE]`——控制器写入审阅包的路径（`scripts/review-package PLAN_FILE BASE HEAD` 会打印其唯一路径；该审阅包不会进入控制器的上下文）

**审阅者返回：**规范符合性结论（✅/❌/⚠️）、优点、问题（Critical/Important/Minor）、任务质量结论
