# 系统化调试

## 概述

**核心原则：** 始终在尝试修复之前找到根因。修复症状等于失败。

**违反流程的字面要求，就是违反调试的精神。**

## 铁律

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

如果你还没有完成阶段 1，就不能提出修复方案。

## 何时使用

适用于任何技术问题：
- 测试失败
- 生产环境中的 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**尤其要在以下情况下使用：**
- 时间紧迫时（紧急情况容易让人想要猜测）
- “先快速修一下”看起来很明显时
- 你已经尝试过多次修复时
- 之前的修复没有奏效时
- 你并不完全理解问题时

**不要在以下情况下跳过：**
- 问题看起来很简单（简单的 bug 也有根因）
- 你很赶时间（仓促行事必然导致返工）
- 经理要求立即修好（系统化调试比反复试错更快）

## 四个阶段

你必须完成每个阶段后才能进入下一个阶段。

### 阶段 1：根因调查

**在尝试任何修复之前：**

1. **仔细阅读错误消息**
   - 不要跳过错误或警告
   - 它们通常包含确切的解决方案
   - 完整阅读堆栈跟踪
   - 记录行号、文件路径、错误代码

2. **稳定地复现**
   - 你能可靠地触发它吗？
   - 确切步骤是什么？
   - 每次都会发生吗？
   - 如果无法复现 → 收集更多数据，不要猜测

3. **检查近期更改**
   - 哪些变更可能导致了问题？
   - Git diff、最近的提交
   - 新依赖、配置更改
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统包含多个组件时（CI → 构建 → 签名、API → 服务 → 数据库）：**

   **在提出修复方案之前，添加诊断插桩：**
   ```
   For EACH component boundary:
     - Log what data enters component
     - Log what data exits component
     - Verify environment/config propagation
     - Check state at each layer

   Run once to gather evidence showing WHERE it breaks
   THEN analyze evidence to identify failing component
   THEN investigate that specific component
   ```

   **示例（多层系统）：**
   ```bash
   # Layer 1: Workflow
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # Layer 2: Build script
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # Layer 3: Signing script
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # Layer 4: Actual signing
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这会揭示：** 哪一层失败（密钥 → 工作流 ✓，工作流 → 构建 ✗）

5. **追踪数据流**

   **当错误位于调用栈深处时：**

   请参见本目录中的 `root-cause-tracing.md`，了解完整的向后追踪技术。

   **快速版本：**
   - 错误值从哪里产生？
   - 谁用错误值调用了这里？
   - 持续向上追踪，直到找到源头
   - 在源头修复，而不是在症状处修复

### 阶段 2：模式分析

**在修复之前找到模式：**

1. **寻找可工作的示例**
   - 在同一代码库中找到类似的可工作代码
   - 与出问题的代码相似的部分中，什么是可工作的？

2. **与参考实现比较**
   - 如果正在实现某种模式，完整阅读参考实现
   - 不要略读——阅读每一行
   - 在应用模式之前充分理解它

3. **识别差异**
   - 可工作的部分与出问题的部分有什么不同？
   - 列出每一个差异，无论多么细小
   - 不要假设“这不可能有影响”

4. **理解依赖关系**
   - 它需要哪些其他组件？
   - 需要哪些设置、配置、环境？
   - 它有哪些假设？

### 阶段 3：假设与测试

**科学方法：**

1. **提出单一假设**
   - 清楚地陈述：“我认为 X 是根因，因为 Y”
   - 把它写下来
   - 要具体，不要含糊

2. **最小化测试**
   - 做出测试假设所需的最小改动
   - 一次只改变一个变量
   - 不要同时修复多个问题

3. **在继续之前验证**
   - 有效吗？是 → 阶段 4
   - 无效？提出新的假设
   - 不要在上面叠加更多修复

4. **当你不知道时**
   - 说“我不理解 X”
   - 不要假装知道
   - 请求帮助
   - 进一步研究

### 阶段 4：实现

**修复根因，而不是症状：**

1. **创建失败测试用例**
   - 尽可能简单的复现
   - 如果可能，使用自动化测试
   - 如果没有测试框架，使用一次性测试脚本
   - 修复之前必须有测试
   - 使用 `superpowers:test-driven-development` 技能编写正确的失败测试

2. **实现单一修复**
   - 处理已识别的根因
   - 一次只做一个更改
   - 不要“顺便”改进
   - 不要捆绑重构

3. **验证修复**
   - 现在测试通过了吗？
   - 其他测试没有被破坏吗？
   - 问题真的解决了吗？
   - 在声称成功之前，使用 `superpowers:verification-before-completion` 技能

4. **如果修复没有奏效**
   - 停止
   - 计数：你尝试了多少次修复？
   - 如果少于 3 次：回到阶段 1，结合新信息重新分析
   - **如果大于等于 3 次：停止并质疑架构（见下面的第 5 步）**
   - 没有架构讨论，不要尝试修复 #4

5. **如果 3 次以上修复失败：质疑架构**

   **显示架构问题的模式：**
   - 每次修复都在不同位置暴露出新的共享状态/耦合/问题
   - 修复需要“大规模重构”才能实现
   - 每次修复都在其他地方产生新的症状

   **停止并质疑基本假设：**
   - 这种模式从根本上合理吗？
   - 我们是不是“仅仅因为惯性而坚持下去”？
   - 应该重构架构，还是继续修复症状？

   **在尝试更多修复之前，与你的用户伙伴讨论**

   这不是失败的假设——这是错误的架构。

## 红旗信号——停止并遵循流程

如果你发现自己在想：
- “先快速修一下，之后再调查”
- “就试着改 X，看看是否有效”
- “一次加多个改动，再运行测试”
- “跳过测试，我手动验证就好”
- “大概是 X，让我修一下”
- “我并不完全理解，但这可能有效”
- “模式说应该是 X，但我要用不同方式调整”
- “主要问题是：[列出修复方案，却没有调查]”
- 在追踪数据流之前提出解决方案
- **“再试一次修复”（已经尝试过 2 次以上时）**
- **每次修复都在不同位置暴露出新问题**

**所有这些都意味着：停止。回到阶段 1。**

**如果 3 次以上修复失败：**质疑架构（见阶段 4.5）

## 你的用户伙伴表明你做错了的信号

**留意这些重新引导：**
- “难道不是这样吗？”——你在未经验证的情况下做了假设
- “它会向我们展示……吗？”——你应该添加证据收集
- “停止猜测”——你在未理解问题的情况下提出修复方案
- “彻底想清楚”——质疑基本假设，而不仅是症状
- “我们卡住了吗？”（沮丧）——你的方法不起作用

**看到这些信号时：**停止。回到阶段 1。

## 常见合理化借口

| 借口 | 现实 |
|--------|---------|
| "Issue is simple, don't need process" | 简单的问题也有根因。流程对简单 bug 也很快。 |
| "Emergency, no time for process" | 系统化调试比猜测和反复试错更快。 |
| "Just try this first, then investigate" | 第一个修复会决定模式。从一开始就正确执行。 |
| "I'll write test after confirming fix works" | 未测试的修复不会稳固。先写测试可以证明修复。 |
| "Multiple fixes at once saves time" | 无法隔离什么起了作用。还会造成新的 bug。 |
| "Reference too long, I'll adapt the pattern" | 不完整的理解必然导致 bug。完整阅读。 |
| "I see the problem, let me fix it" | 看到症状不等于理解根因。 |
| "One more fix attempt" (after 2+ failures) | 3 次以上失败 = 架构问题。质疑模式，不要再次修复。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根因** | 阅读错误、复现、检查更改、收集证据 | 理解 WHAT 和 WHY |
| **2. 模式** | 寻找可工作示例、比较 | 识别差异 |
| **3. 假设** | 建立理论、最小化测试 | 已确认或形成新假设 |
| **4. 实现** | 创建测试、修复、验证 | bug 已解决，测试通过 |

## 当流程揭示“没有根因”时

如果系统化调查揭示问题确实是环境、时间相关或外部因素导致的：

1. 你已经完成了流程
2. 记录你调查过的内容
3. 实现适当的处理（重试、超时、错误消息）
4. 添加监控/日志，以便未来调查

**但是：** 95% 的“没有根因”案例都是调查不完整。
